Executive Summary

This project presents a concurrent medical telemetry and automated facility management firmware prototype engineered for the Espressif ESP32 dual-core microcontroller. Designed to satisfy all 6 mandatory internship assignments within a single, unified codebase, the system integrates physical sensor acquisition, real-time physiological signal synthesis, role-based cloud publishing via MQTT, closed-loop safety actuation, and an advanced fault-tolerant offline detection and replay engine.

The firmware executes on FreeRTOS Symmetric Multiprocessing (SMP), allocating network protocol stacks (Wi-Fi and lwIP) to Core 0 while assigning all 13 prioritized application tasks (coexisting with Arduino's low-overhead loopTask) to Core 1. Inter-task communication is strictly synchronized using thread-safe FreeRTOS mutexes, queues, and spinlocks to prevent race conditions across shared telemetry and peripherals. A dual-tier watchdog supervisor couples the hardware ESP-IDF Task Watchdog Timer (TWDT) with an application heartbeat monitor to provide robust supervisory fault detection and automated recovery.

Key Project Accomplishments:
  • Unified Single-Project Integration: All 6 assigned internship tasks run simultaneously in one firmware image with zero Arduino delay() calls (FreeRTOS tasks use cooperative vTaskDelay() yielding).
  • Resource Efficiency: Static RAM utilization measured at 15.1% (49,536 B of 327,680 B data SRAM budget; 520 KB physical on-chip SRAM) and Flash at 80.2% (1,051,506 B of 1,310,720 B), leaving healthy runtime dynamic heap for FreeRTOS queues.
  • Automated Test Suite: 24 Unity test cases are included, covering strict numeric parsers, medication safety, slew-rate mechanics, telemetry validity, sensor-fault transitions and queue-retry bookkeeping. The ESP32 test runner has been build-verified.
  • Open Source & Credentials Safety: Released under the MIT License with complete credential isolation (private keys never committed to Git).
Engineering Prototype & Educational Simulation Disclaimer: This firmware project is an embedded systems engineering prototype and educational simulation developed for technical evaluation. It is not a certified medical device and must not be used for actual clinical diagnostics, patient care, life support, or operational medical administration.

2. Concurrency Model & FreeRTOS Task Scheduling (Task 1)

The system utilizes FreeRTOS Symmetric Multiprocessing (SMP) to execute 13 application tasks concurrently across a strict priority hierarchy. All 13 application worker tasks are pinned to Core 1, alongside Arduino loopTask. Wi-Fi and lwIP networking tasks are configured for Core 0, while other system tasks may execute according to their configured affinity.

Task Identifier Priority Execution Cadence Stack Allocation Task Responsibilities & Synchronization
watchdogTask Priority 4 1000 ms periodic 4096 Bytes Audits task heartbeats (6000 ms silence limit); feeds ESP-IDF TWDT (8000 ms panic).
vitalTask Priority 3 5s to 60s adaptive 4096 Bytes Generates optical PPG (HR & SpO2); queries adaptive cadence via getSamplePeriodMs() (managed by samplingTask via samplingQueue).
ecgTask Priority 3 Fixed 5 Hz (200 ms) 4096 Bytes Synthesizes real-time cardiac Gaussian waveform morphology.
medicationTask Priority 3 50 Hz (20 ms loop) 4096 Bytes Enforces +5.0 mg/hr/s slew rate, button debounce, rapid 3.3 Hz alarm; holds dose at 80 mg/hr.
bedTask Priority 2 50 Hz (20 ms loop) 4096 Bytes Computes 500-2400 μs servo PWM pulse; smooth slew (1.5°/s auto, 2.0°/s manual, 5.0°/s emergency).
temperatureTask Priority 2 Non-blocking FSM 4096 Bytes Non-blocking 2-state machine (TEMP_IDLE → TEMP_CONVERTING) managing DS18B20 ≥800 ms acquisition via millis() gate.
motionTask Priority 2 1000 ms periodic 4096 Bytes Samples HC-SR501 PIR sensor; detects bed departure/occupancy.
samplingTask Priority 2 1000 ms periodic 4096 Bytes Monitors vital health state; commands 5s abnormal vs 60s stable acquisition rate.
environmentTask Priority 2 1000 ms periodic 4096 Bytes Simulates facility room temp, O2, and AQI with CLI override support.
alertTask Priority 2 Asynchronous (Event) 4096 Bytes Blocks on alertSemaphore; dispatches rising-edge clinical and facility anomalies.
offlineTask Priority 2 50 ms periodic 4096 Bytes Evaluates Wi-Fi/MQTT health, drives acoustic failure patterns, and buffers telemetry.
mqttTask Priority 2 3000 ms round-robin 8192 Bytes PubSubClient transport, exponential backoff (1s to 30s), and FIFO offline replay.
displayTask Priority 1 100 ms periodic 4096 Bytes Drains sensorQueue (depth 16), updates telemetry, renders OLED medication UI and offline banner.

Note on Simulation CLI: Interactive UART simulation commands (e.g. SET_HR, SET_TEMP, SIM_OFFLINE) are parsed within Arduino's standard loop() (loopTask), running with 1000 ms delay yielding.

Inter-Task Synchronization Primitives

  • telemetryMux: Spinlock critical section (portMUX_TYPE) protecting shared clinical and facility telemetry with zero context-switch latency.
  • displayMutex: FreeRTOS Mutex (xSemaphoreCreateMutex()) serializing I2C bus transactions to the SSD1306 OLED display.
  • heartbeatMutex: FreeRTOS Mutex protecting the monitored task watchdog timestamp tracking table.
  • alertSemaphore: Binary semaphore (xSemaphoreCreateBinary()) signaling alertTask on clinical or facility state transitions.
  • sensorQueue: 16-slot FreeRTOS queue (xQueueCreate(16, sizeof(SensorMessage))) delivering sensor data to displayTask.
  • samplingQueue: Single-element FreeRTOS queue (xQueueCreate(1, sizeof(uint32_t))) with overwrite semantics delivering doctor sampling rate overrides from MQTT.
  • bedQueue: Single-element FreeRTOS queue (xQueueCreate(1, sizeof(float))) with overwrite semantics delivering doctor bed elevation angle overrides from MQTT.
  • offlineBuffer: 64-slot FreeRTOS RAM queue storing outbound MQTT messages (topic + payload) without timestamps during network outages, drained in FIFO order upon reconnect.

5. Comprehensive Implementation of Assignment Tasks

Task 1: Multi-Sensor Expansion Using FreeRTOS

The system concurrently manages physical and simulated parameters. Physical core temperature is sampled via a Dallas DS18B20 1-Wire sensor on GPIO 4 using a non-blocking two-state machine (TEMP_IDLE → TEMP_CONVERTING). This ensures the ≥800 ms 12-bit conversion delay (checked via non-blocking millis() gate in sensors.cpp) never stalls the FreeRTOS scheduler. Optical Photoplethysmogram (PPG) vitals (Heart Rate 50-100 BPM, SpO2 92-100%) and a 5 Hz Gaussian ECG waveform model are synthesized concurrently with independent tiered threshold monitoring across all vital modalities (Heart Rate, ECG Rate, SpO2, and Body Temperature). Dual-tier watchdog protection couples the hardware ESP-IDF TWDT (8000 ms hardware panic) with a software heartbeat monitor (watchdogTask) auditing the 12 FreeRTOS worker tasks every 1000 ms against a 6000 ms silence limit while servicing its own hardware TWDT registration.

Task 2: Dual-Role IoT Monitoring System (Role-Based Dashboards)

The system publishes to 10 dedicated Adafruit IO feeds, enforcing logical separation between clinical and facility personnel:

  • Medical Staff Feeds: medical-heart-rate, medical-spo2, medical-body-temperature.
  • Facility Management Feeds: facility-room-temperature, facility-oxygen, facility-aqi.
  • Control & Events: medication-dosage, bed-angle, sampling-rate, and hospital-events.

Every 60 seconds, mqttTask computes cumulative statistical metrics across all sensors, publishing a structured multi-line diagnostic summary (HOSPITAL SUMMARY) to hospital-events. The summary explicitly distinguishes discrete physiological sensor acquisitions (Samples: accumulated only when fresh clinical vital packets arrive — ~1/min in stable mode, ~12/min in abnormal mode) from facility supervisory observations (Snapshots: sampled every 3-second MQTT evaluation tick — ~20/min), alongside anomaly counts and physiological extrema, resetting the accumulators after each transmission.

Task 3: Smart Medication Dosage Adjustment System

Doctors remotely command infusion dosage (0-100 mg/hr) via dashboard slider. The firmware implements a multi-tier safety interlock:

  • Safety Tiers: Normal (0.0 - 79.9 mg/hr, Solid Green LED), Warning (80.0 mg/hr, Solid Yellow LED), and Critical (>80.0 mg/hr).
  • Rate Limiting: Maximum upward slew rate clamped to +5.0 mg/hr per second (MEDICATION_RATE_LIMIT_STEP_MG_PER_SEC = 5.0f), preventing abrupt dosage spikes.
  • Dual-Channel Physical Bedside Interlock: Any commanded dosage >80 mg/hr clamps the applied rate at 80.0 mg/hr, flashes the Red LED and 1200 Hz buzzer rapidly at ~3.3 Hz (300 ms period: 150 ms ON / 150 ms OFF), and prompts PRESS BUTTON on the OLED. The applied dosage remains held at 80.0 mg/hr indefinitely until the clinician physically confirms the override by pressing the bedside button on GPIO 13 or reduces the target dosage back to ≤80 mg/hr. Range Authorization Policy: Once physically confirmed at bedside for a critical rate, adjustments within the critical band (>80.0 mg/hr) remain authorized without re-prompting; dropping dosage back to ≤80.0 mg/hr automatically clears confirmation and re-arms the interlock.

Task 4: Intelligent Remote Bed Elevation Control

Bed elevation is driven by an SG90 micro-servo on GPIO 18 (500 μs to 2400 μs pulse width) with smooth microsecond pulse interpolation to protect patient comfort. The autonomous controller dynamically maps clinical condition to posture:

  • Sleeping Mode (10°, 1.5°/s): Nominal resting position when vitals are stable.
  • Breathing Support Mode (45°, 1.5°/s): Automatically triggered when SpO2 drops into the warning band (88% - 91%) to alleviate pulmonary pressure.
  • Emergency Mode (90°, 5.0°/s): Automatically triggered immediately upon any Critical vital sign (cardiac arrest, extreme hypothermia).
  • Clinician-in-the-Loop Override Primacy (0°-90°, 2.0°/s): Remote slider allows attending physicians to command any posture with full clinical authority (e.g. flattening the bed to 0° supine for CPR chest compressions or surgical access during a cardiac arrest). Any subsequent transition in the patient's bed posture category (SLEEPING ↔ BREATHING_SUPPORT ↔ EMERGENCY) automatically cancels manual override and re-evaluates posture.

Task 5: Smart Dynamic Sampling Rate (Adaptive Monitoring)

To optimize battery life and bus utilization, samplingTask dynamically adjusts the sensor acquisition (sampling) interval based on patient stability (while MQTT telemetry transmission remains on its independent 3-second round-robin cycle):

  • Abnormal State: Once an abnormal vital sign is acquired, sampling automatically accelerates to 5 seconds. (During 60-second stable mode, discrete sampling introduces an acquisition latency of up to 60 seconds before an acute vital fluctuation is sampled).
  • Stable State: Automatically relaxes sampling to 60 seconds (AUTO_INTERVAL_STABLE_MS = 60000) when vitals return to normal.
  • Manual Override: Dashboard slider permits clinician adjustments between 5 and 60 seconds. Clinical severity escalation to Critical immediately revokes slower overrides.

Task 6: Advanced Offline Detection (Fault-Tolerant System)

The firmware continuously monitors Wi-Fi and MQTT connectivity to maintain a tri-state health machine (ONLINE, DEGRADED, OFFLINE):

  • OLED Notification: Inverted status bar on bottom rows (y: 54..63) displays LOGGING OFFLINE without obstructing medication data.
  • Acoustic Discrimination: Wi-Fi failure triggers a rapid double-pip tone (0-100 ms, 200-300 ms ON), while MQTT failure triggers a slow single beep (0-500 ms ON).
  • FIFO Offline Buffer: An in-memory queue stores up to 64 telemetry records (~36.8 KB SRAM) providing best-effort local data retention during transport outages under QoS 0 at-most-once delivery. Timestamps are assigned upon broker receipt during replay.
  • Exponential Backoff & Replay: Reconnection retry delay doubles from 1s up to 30s (1s → 2s → 4s ... → 30s max). Upon reconnection, mqttTask drains buffered records in FIFO order, sharing the 3000 ms round-robin slot (20 msgs/min baseline); event bursts and 60 s summaries contribute toward Adafruit IO's 30 data points/minute quota.

Known Architectural Limitations & Design Notes

  1. Multiplexed Event Feed (Adafruit IO Quotas): Due to Adafruit IO's 10-feed limit on standard accounts (6 sensor feeds + 3 control feeds + 1 event feed), all clinical alerts, facility alerts, and 60-second summary reports are multiplexed onto the single shared hospital-events feed.
  2. Logical Role Separation: Role separation between Medical Staff and Facility Management dashboards is implemented at the topic and dashboard layout level rather than through enforced multi-tenant cryptographic access control (RBAC).
  3. Replayed Telemetry Arrival Timestamps: Replayed offline records carry the timestamp of broker reconnection/receipt rather than historic capture time due to Adafruit IO's standard MQTT ingestion format and absence of an onboard battery-backed RTC.
  4. Bounded FIFO RAM Buffer: The offline buffer utilizes an in-memory FreeRTOS queue holding up to 64 records of 576 bytes each (~36.8 KB SRAM) under QoS 0 at-most-once delivery. When capacity is reached, it drops newest incoming records to protect initial fault events. It is RAM-only and volatile upon power cycle or hardware reset.
  5. Task Watchdog & SYSTEM_DEGRADED Window: SYSTEM_DEGRADED indicates an internal FreeRTOS worker task has starved its heartbeat while transport remains active. The ESP-IDF Task Watchdog Timer (TWDT) enforces an 8000 ms panic threshold; if a task hangs permanently, the chip resets ~2 seconds after entering SYSTEM_DEGRADED to provide automatic recovery (simulation only).
  6. Simulated Sensor Telemetry: In simulation mode, physiological vitals (PPG, ECG) and ambient facility conditions (Room Temp, Oxygen %, AQI) are synthesized via mathematical models (e.g. Gaussian superposition) and UART CLI overrides (SET_HR, SET_SPO2, SET_TEMP, SET_ROOM, SET_OXYGEN, SET_AQI).
  7. Timer Rollover & Reconnection Hygiene: Network retry timers employ signed modular delta arithmetic ((int32_t)(now - nextRetryMs) ≥ 0) combined with active timestamp refreshes during healthy connectivity (nextRetryMs = now;), systematically preventing both 49.7-day 32-bit millis() rollover lockups and long-uptime signed subtraction stalls.
  8. Simulated Medication Dosage Controller: Task 3 demonstrates software-in-the-loop rate limiting (+5 mg/hr/sec), physical button confirmation interlocks, and alert arbitration. It models infusion pump control logic; physical pump actuators or verified flow sensors are not included in the BOM.
  9. Network Security: The prototype connects using standard unencrypted MQTT on port 1883 for Wokwi simulation simplicity. For physical hospital networks, TLS 1.3 on port 8883 with certificate verification is recommended.
  10. Summary Reporting Window Durations: The periodic 60-second hospital summary report (REPORT_INTERVAL_MS = 60000) aggregates telemetry over its nominal 1-minute window. If MQTT publication or buffer queuing temporarily fails during network degradation, the window automatically extends beyond 60 seconds until transmission or buffering succeeds, resetting the sample accumulator only upon confirmed delivery to ensure zero metric loss.
  11. Sensor Availability vs. Clinical Status Integrity: Sensor availability is decoupled from physiological stability via a 3-state telemetry model (INITIALIZING, SENSOR FAULT, READY). During initialization, clinical NORMAL clearance is suppressed until all required telemetry channels are initialized and verified valid. Confirmed abnormalities in available channels may still be reported independently. Confirmed hardware failures (e.g., DS18B20 85°C scratchpad reset or disconnected wire) are reported immediately during initialization as an explicit SENSOR FAULT once confirmed. Sensor recovery triggers a SENSOR RESTORED event followed by prompt clinical re-evaluation bypassing the standard 60-second cooldown. Crucially, sensor availability events use an independent publication path without modifying the clinical alert timer (lastMedicalAlertPublishMs) or extending its existing cooldown. Concurrent vital abnormalities (e.g. tachycardia, hypoxia) remain fully detectable and are published subject to configured clinical alert rate limits even during an active temperature sensor fault.
  12. Actuator Power Supply Isolation: In the Wokwi simulation environment, the SG90 servo motor is powered directly from the ESP32 development board's 5V rail. For physical clinical bed deployments, a separate regulated 5V supply with a common ground is required to prevent actuator inductive kickback and stall current transients from causing ESP32 brownout resets.

7. Verification Suite & Interactive Simulation Manual

Automated Unit Testing (PlatformIO Unity)

Unit tests implemented under test/test_main.cpp define 24 test cases covering strict numeric string parsers (validating against NaN, Infinity, negative boundaries, float integers, and trailing characters), medication dosage safety clamping, discrete clinical tiers, rate-limiting slew mechanics (20 ms increments, long interruption recovery, timer rollover, immediate downward adjustment), multi-parameter telemetry validity gating, sensor-fault state machine transitions and recovery, and DS18B20 invalidation queue-retry resilience.

Test Architecture & Coverage Qualification: Tests #1 through #22 exercise production parsers, medication controllers, and validity gating helpers. Tests #23 and #24 directly execute extracted production state helpers (evaluateSensorFaultTransition, applySensorFaultTransition, and updateQueueRetryState) to verify state-transition bookkeeping and queue-retry logic across initialization, fault activation, recovery, and FIFO pending transitions. These unit tests isolate algorithmic and state correctness without mocking or claiming full integration over live FreeRTOS queue saturation or physical MQTT broker network transport.

The test suite is build-verified using PlatformIO: 

pio test -e esp32dev --without-uploading --without-testing

Build-Verification Note: The --without-testing flag compiles and links the complete Unity test framework and test runner binary for the ESP32 Xtensa architecture to verify code correctness and build integrity. Execution of assertions with pass/fail counts occurs when connected to an ESP32 target via pio test -e esp32dev (which halts at the upload stage if no physical USB serial device is attached to the workstation).

8. Conclusion & Engineering Reflection

The Smart Hospital IoT System demonstrates production-oriented embedded engineering by combining concurrent multitasking, non-blocking asynchronous state machines, robust fail-safe hardware watchdogs, and fault-tolerant cloud communication within the constraints of an ESP32 microcontroller. By executing all 6 internship assignments simultaneously in a single integrated project, the system ensures effective embedded multitasking, patient safety interlocks, and operational resilience.
