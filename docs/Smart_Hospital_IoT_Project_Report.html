1. Executive Summary & Project Scope

Modern critical care hospital infrastructure demands real-time monitoring of acute physiological vitals alongside facility environmental parameters. Traditional embedded firmware architectures that rely on monolithic superloops or blocking delay functions (delay()) are fundamentally inadequate for healthcare IoT applications; a single blocking thermal conversion or network reconnection can freeze vital alarm processing, resulting in life-threatening latency.

This project delivers an enterprise-grade, concurrent medical telemetry and facility management firmware engineered for the dual-core Espressif ESP32 microcontroller using FreeRTOS Symmetric Multiprocessing (SMP). All six assigned internship tasks have been architected and implemented within a single, unified codebase:

  • Task 1 (Multi-Sensor Expansion): Concurrent FreeRTOS execution of real-time clinical parameters (Dallas DS18B20 body temperature, PIR motion, synthetic PPG pulse oximetry, and 5 Hz Gaussian ECG synthesis) protected by a dual-tier hardware/software watchdog timer.
  • Task 2 (Dual-Role IoT Monitoring): Strict segregation of data into a Medical Staff Dashboard and a Facility Management Dashboard published to dedicated MQTT topics with predefined safe thresholds and 60-second aggregated statistical insights.
  • Task 3 (Smart Medication Dosage Safety): High-precision remote medication infusion slider (0–100 mg/hr) featuring OLED real-time rendering, slew-rate clamping (+10 mg/hr/s), rapid 3.3 Hz red LED and buzzer alarms above 80 mg/hr, and mandatory physical push-button confirmation.
  • Task 4 (Intelligent Remote Bed Elevation Control): Remote bed articulation (0–90°) driven by an SG90 micro-servo motor with smooth pulse-width interpolation slew rate, featuring automatic clinical posture triggers (Emergency 90°, Breathing Support 45°, Sleeping 10°) based on live patient vitals.
  • Task 5 (Smart Dynamic Sampling Rate): Dual-mode telemetry frequency adaptation dynamically accelerating from a battery-conserving 30s–60s cadence to a 5-second high-frequency stream upon detecting abnormal physiological conditions.
  • Task 6 (Advanced Offline Detection & Fault Tolerance): Resilient tri-state supervisor (ONLINE, DEGRADED, OFFLINE) activating persistent OLED LOGGING OFFLINE banners, failure-specific acoustic buzzer cadences, a 64-item RAM FIFO fallback queue (~36.8 KB SRAM), and automated cloud synchronization via exponential backoff replay upon network restoration.

2. System Architecture & Concurrency Model

The ESP32 features a dual-core 32-bit Xtensa LX6 microprocessor. To eliminate latency jitter on clinical alarms, the system implements strict asymmetric core pinning:

  • Core 0 (Dedicated Network Infrastructure): Runs the Espressif 802.11 b/g/n Wi-Fi PHY/MAC stack and the lwIP TCP/IP stack. High-overhead wireless encryption, beacon tracking, and packet framing are completely isolated from medical tasks.
  • Core 1 (Application Worker Pool): Dedicated exclusively to FreeRTOS application threads (12 prioritized tasks), guaranteeing deterministic execution of clinical decision loops.

4. Detailed Task Implementation & Engineering Solutions

4.1 Task 1: Multi-Sensor Expansion & Concurrency Supervision

The firmware integrates five distinct sensor telemetry streams:

  • Dallas DS18B20 (1-Wire, GPIO 4): Standard 12-bit Dallas temperature sensors require up to 750 ms to complete an analog-to-digital thermal conversion. Calling blocking library functions like requestTemperatures() inside a real-time system is unacceptable. The firmware implements a two-state non-blocking finite state machine (FSM): 
    State 1 (TEMP_IDLE): Calls sensors.setWaitForConversion(false); issues conversion command; transitions to TEMP_CONVERTING.
State 2 (TEMP_CONVERTING): Checks millis() elapsed time. Yields scheduler via vTaskDelay() until 750 ms elapses, then reads scratchpad.
  • HC-SR501 PIR Sensor (GPIO 27): Dedicated motion detection for patient bed occupancy and room entry tracking.
  • Photoplethysmogram (PPG) Synthesis: Heart rate (50–100 BPM) and SpO2 (92–100%) simulated physiological stream with interactive serial CLI overrides (SET_HR, SET_SPO2).
  • Continuous ECG Waveform Synthesis: Synthesizes real-time cardiac morphology at 5 Hz (200 ms cadence) using a Gaussian superposition model simulating P-wave, QRS complex, and T-wave electrical depolarization.
  • Dual-Tier Watchdog Architecture:
    1. Hardware Watchdog (TWDT): Initialized via ESP-IDF esp_task_wdt_init(8000, true) with an 8000 ms panic threshold that triggers an intentional hardware reboot if a core locks.
    2. Application Heartbeat Supervisor: watchdogTask audits registered task heartbeat timestamps every 6000 ms. If any worker task stalls, the system transitions to SYSTEM_DEGRADED to emit diagnostic alerts before the hardware watchdog forces a reset.

4.3 Task 3: Smart Medication Dosage Adjustment System

Remote control of medication infusion pumps involves inherent clinical risk. The firmware implements a defense-in-depth safety pipeline preventing abrupt dosing errors:

  • Slew-Rate Limiting: Even if a clinician commands an abrupt leap from 10 mg/hr to 75 mg/hr via the dashboard slider, the internal mathematical rate limiter restricts dosage increases to a maximum ramp of +10.0 mg/hr per second (calculated at 50 Hz in medicationTask).
  • Three-Tier Safety Classification:
    • Normal (0.0 – 79.9 mg/hr): Solid Green LED on GPIO 33; silent buzzer.
    • Warning (80.0 mg/hr): Solid Yellow LED on GPIO 26; silent buzzer.
    • Critical (> 80.0 mg/hr): Rapid 3.3 Hz flashing of Red LED on GPIO 25 and synchronous acoustic pulsing of the 1.2 kHz Piezo Buzzer on GPIO 14.
  • Physical Push-Button Two-Factor Interlock: Any dosage command exceeding 80.0 mg/hr is clamped at 80.0 mg/hr and enters the DOSAGE_PENDING_CONFIRMATION state. The SSD1306 OLED displays CRITICAL REQUEST - PRESS BUTTON. A healthcare clinician must physically depress the green pushbutton on GPIO 13 within 5.0 seconds (debounced with 50 ms hysteresis) to authorize the critical infusion. If unconfirmed within 5.0 seconds, the request aborts safely.

4.4 Task 4: Intelligent Remote Bed Elevation Control

An SG90 micro-servo motor connected to GPIO 18 articulates the hospital bed elevation between 0° (flat) and 90° (upright). Abrupt mechanical movements cause patient distress; bedTask implements smooth pulse-width modulation (PWM) interpolation:

  • PWM Slew Interpolation: Converts target degrees to microsecond pulses (500 μs = 0°, 2400 μs = 90°). Target angles are approached smoothly at 1.5°/second in autonomous mode and 2.0°/second in manual mode.
  • Autonomous Clinical Posture State Machine:
    • Emergency Mode (90°): The bed immediately elevates to maximum vertical angle (90°) upon detection of any critical vital parameter (Acute Tachycardia, Bradycardia, Extreme Hypothermia, or Hyperthermia) to facilitate emergency cardiac intervention.
    • Breathing Support Mode (45°): When blood oxygen saturation drops into the warning threshold (88%–91% SpO2), the bed automatically articulates to Fowler's posture (45°) to reduce pulmonary pressure and promote alveolar ventilation.
    • Sleeping Rest Mode (10°): When all vital parameters remain within nominal physiological boundaries, the bed returns to a 10° resting incline.
  • Manual Clinician Override: Clinicians can command specific angles (0–90°) via the hospital-bed-angle dashboard slider or interactive serial CLI (SET_BED <deg>).

4.5 Task 5: Smart Dynamic Sampling Rate (Adaptive Monitoring)

Continuous high-frequency radio transmission depletes battery reserves and consumes cloud IoT ingestion quotas. samplingTask continuously evaluates patient risk and adjusts telemetry cadence dynamically:

  • Nominal Physiological State: Relaxes sensor acquisition to 30 to 60 seconds, drastically reducing radio on-time and power draw.
  • Abnormal State (Warning or Critical): Automatically accelerates sampling frequency to 5 seconds to capture high-resolution physiological dynamics during clinical deterioration.
  • Non-Blocking Queue Distribution: Frequency updates are pushed to sensor worker tasks via FreeRTOS samplingRateQueue without locking execution.

4.6 Task 6: Advanced Offline Detection & Cloud Synchronization

Hospital Wi-Fi networks suffer from RF interference, access point handoffs, and temporary router outages. An enterprise healthcare device must guarantee zero patient data loss during connectivity failures.

  • Tri-State System Health Engine:
    1. STATE_ONLINE: Wi-Fi connected, MQTT broker active, all FreeRTOS task heartbeats valid.
    2. STATE_DEGRADED: Network transport active, but an internal worker task missed its 6000 ms heartbeat audit.
    3. STATE_OFFLINE: Wi-Fi association severed or MQTT broker unreachable.
  • Non-Destructive OLED Status Banner: Upon entering offline mode, the bottom 10 pixels of the SSD1306 display (row 54..63) render a high-contrast inverted bar with LOGGING OFFLINE. The upper display area (row 0..44) continues rendering live medication dosage, ensuring that network failures never compromise local clinical visibility.
  • Failure-Specific Acoustic Buzzer Cadences: The firmware drives GPIO 14 with distinct rhythmic patterns allowing nursing staff to immediately diagnose network fault types without inspecting a console:
    • Wi-Fi Disconnected (BUZZER_MODE_WIFI_FAIL): Rapid double-pip acoustic pattern (100 ms ON, 100 ms OFF, 100 ms ON, 700 ms OFF).
    • MQTT Broker Disconnected (BUZZER_MODE_MQTT_FAIL): Slow single-beep cadence (500 ms ON, 500 ms OFF).
    • Priority Arbitration: If a clinical medication emergency occurs while offline, the medical alarm immediately supersedes network failure tones.
  • Bounded FIFO RAM Buffer: Outbound telemetry records are packaged into OfflineTelemetryItem structures and enqueued into a dedicated FreeRTOS queue holding up to 64 records (~36.8 KB SRAM). When full, the queue drops newest incoming records to protect historical fault event records.
  • Automated Reconnection & Replay with Exponential Backoff: Reconnection attempts employ an exponential backoff algorithm starting at 2000 ms and doubling up to 60,000 ms (2s → 4s → 8s → 16s → 32s → 60s) to prevent broker flood. Upon successful reconnection, the buzzer silences, the OLED offline banner clears, and mqttTask drains the 64-item FIFO buffer sequentially to Adafruit IO.

8. Known Architectural Limitations & Design Notes

In compliance with rigorous engineering documentation standards, the following six design trade-offs are explicitly noted:

  1. Multiplexed Event Feed (Adafruit IO Quotas): Adafruit IO enforces a strict limit of 10 feeds on free accounts. The firmware utilizes 6 feeds for telemetry (Heart Rate, SpO2, Body Temp, Room Temp, Room Oxygen, AQI), 3 feeds for bi-directional control (Dosage, Bed Angle, Sampling Rate), and multiplexes all clinical alarms, facility warnings, and 60-second summary reports onto the single shared hospital-events topic.
  2. Logical Role Separation: The segregation between Medical Staff and Facility Management dashboards is implemented at the topic and dashboard layout level rather than via cryptographic multi-tenant access control (RBAC).
  3. Replayed Telemetry Arrival Timestamps: Offline records replayed to Adafruit IO carry the broker reconnection timestamp rather than original sampling time due to standard Adafruit IO MQTT ingestion constraints and the absence of a battery-backed physical RTC.
  4. Bounded FIFO RAM Buffer: The offline buffer utilizes an in-memory FreeRTOS queue holding 64 records (~36.8 KB SRAM). When capacity is exceeded during extended outages, newest records are dropped to preserve early failure data. Data is volatile across power cycles.
  5. Task Watchdog & SYSTEM_DEGRADED Window: SYSTEM_DEGRADED indicates a worker task starved its heartbeat while transport remained active. The hardware TWDT enforces an 8000 ms panic threshold; if a task hangs permanently, the chip resets ~2 seconds after entering SYSTEM_DEGRADED.
  6. Simulated Sensor Telemetry: In Wokwi simulation mode, PPG, ECG, and ambient room parameters are generated via mathematical models and UART CLI overrides.
